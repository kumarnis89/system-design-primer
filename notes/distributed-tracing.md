# 🔍 Distributed Tracing

## 📌 High-Level Summary
Distributed tracing is a method used to profile and monitor applications, especially those built on microservices architectures. It tracks the lifecycle of a single request as it flows through various network boundaries, queues, and services.

---

## ⚙️ Core Concepts

### 1. The Basics
* **Trace:** Represents the entire journey of a request from start to finish across all services.
* **Span:** The basic building block of a trace. It represents a single unit of work (e.g., an HTTP request, a database query, or a function execution) with a start and end time.
* **Context Propagation:** The mechanism that passes tracing metadata (like Trace IDs and Span IDs) across network boundaries (usually via HTTP headers) so down-stream services know they belong to the same request.

### 2. How Components Work Together
* **Trace ID:** A unique identifier generated by the first service that handles the request. It remains identical across all services.
* **Span ID:** A unique identifier for a specific segment of work. A child span references its parent's Span ID to build a tree structure.

---

## ⚖️ Why We Need It (The Problem vs. Solution)

| Monolithic Architecture | Microservices (Without Tracing) | Microservices (With Tracing) |
| :--- | :--- | :--- |
| Single log file traces the entire request path cleanly. | Logs are scattered across dozens of servers; debugging an error is like finding a needle in a haystack. | **Trace IDs unify logs across all servers**, allowing you to see the exact timeline of a single request instantly. |

---

## 🛠️ Architecture & Tools
A standard tracing pipeline involves:
1. **Instrumentation (SDKs):** Code libraries embedded in your service to generate traces (e.g., **OpenTelemetry**).
2. **Collector:** A proxy that receives, batches, and processes spans from applications.
3. **Storage/Backend:** Where traces are saved (e.g., **Jaeger**, **Zipkin**, **Elasticsearch**).
4. **UI:** Visual timeline charts used to analyze latency bottlenecks.

---

## 🧠 Deep Dive: Trade-offs & Challenges

### 🚀 Sampling Strategies
Because tracing every single request creates massive storage costs and network overhead, systems use sampling:
* **Head-based Sampling:** The decision to trace a request is made at the very beginning (e.g., sample 5% of traffic). *Risk:* You might miss rare errors.
* **Tail-based Sampling:** The system caches all spans and makes the sampling decision at the end. *Benefit:* You can choose to save 100% of errors and anomalies, but it requires heavy memory infrastructure.

### ⚠️ Performance Overhead
Adding trace headers, generating UUIDs, and sending span data over the network uses CPU and memory. Poorly configured tracing can slow down production services.
